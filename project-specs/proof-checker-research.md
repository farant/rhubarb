# Greenfield Design Doctrine for a Maximalist Proof-Checking System: A Research Report by Layer

## TL;DR
- **Fix the logic on paper with settled metatheory first.** The strongest greenfield candidate is a predicative or carefully‑restricted‑impredicative type theory in the **observational/setoid family (TTobs / CIC^obs, Pujet–Tabareau 2022–2025)**, which recovers the exact properties Lean sacrifices. Carneiro's 2019 thesis *The Type Theory of Lean* proves Lean has **no subject reduction, non‑transitive definitional equality, no Church–Rosser, undecidable/possibly non‑terminating checking**; TTobs by contrast "features a notion of reduction that is normalizing and provides an algorithmic canonicity result, which we formally prove in Agda...the decidability of the conversion and of the type checking, as well as consistency." Add classical mathematics (choice, propext, excluded middle) as reduction‑blocking axioms, HOL‑style, rather than baking it into conversion.
- **Concentrate trust in a tiny kernel and run ≥2 independent kernels from day one against a stable export format.** The 2026 Lean kernel bug #14576 (phantom‑parameter nested inductives → an AI‑assisted "disproof" of Collatz) and the OpenAI‑model bug hunt that followed prove that bugs live in *implementations*, not necessarily the theory, and that only differential checking + export‑and‑recheck + adversarial AI reliably catches them.
- **Everything above the kernel is untrusted and must emit kernel‑checkable certificates**: a *specified, deterministic* bidirectional elaborator (the antidote to Lean's "the elaborator is the language" trap); tactics/SMT/SAT/AI via Sledgehammer‑style reconstruction (Alethe, lean‑smt, verified LRAT); and a declarative Mizar/Isar surface for AI‑written, human‑reviewed proofs. Continuous testing (differential, mutation, metatheory fuzzing, a regression corpus of every known soundness bug, an adversarial bounty) and a Palomar‑style statement registry close the loop.

## Key Findings

1. **Lean's metatheoretic compromises are real and documented.** Carneiro's *The Type Theory of Lean* (2019) proves that definitional proof irrelevance in an impredicative Prop + subsingleton (large) elimination + quotients + eta together break transitivity of defeq and subject reduction; the checker can be made to diverge (`#reduce Omega`). Lean's reference manual concedes this while arguing it never bites in practice and does not affect soundness. Consistency is by a Werner‑style ZFC model: ZFC + (n+1) inaccessibles ⊢ Con(Lean with n+1 universes).

2. **The observational/setoid line fixes exactly these problems on paper.** Pujet & Tabareau's TTobs ("Observational Equality: Now For Good", POPL 2022) and CIC^obs ("Observational Equality Meets CIC", ESOP 2024 / TOPLAS 2025) deliver funext, propext, definitional UIP with a normalizing reduction and machine‑checked (Agda) canonicity/decidability/consistency, plus quotient types and Swan Id types. This is the single most important 2022–2026 development for a greenfield kernel.

3. **Small kernels are achievable and are the field's proven trust anchor.** HOL Light's kernel (`fusion.ml`) is ~396–430 lines of OCaml; Metamath's `mmverify.py` is ~350 lines of Python; set.mm is routinely rechecked by five independent verifiers in five languages. This is the de Bruijn criterion in practice.

4. **The 2026 Lean bug wave is the definitive case study.** #14576 (nested‑inductive phantom parameters) produced a `sorry`‑free false "disproof" of Collatz; the independent Rust checker `nanoda` had an *independent* coincident bug. The follow‑up OpenAI‑model hunt (concluded 20 Aug 2026) found more kernel bugs (universe‑normalization Prop recognition #14613, kernel‑type name clashes #14616, **order‑dependent** is_def_eq caching #14806, is_prop needing a sort #14807/#14843) and runtime exploits (reference‑counter overflow #14838; a GMP 6.1.2 bug #14833; multi‑gigabyte numeral exploit → bounded numerals #14849).

5. **Automation with certificates is mature enough to copy.** Sledgehammer reconstruction, the Alethe SMT proof format (veriT/cvc5), lean‑smt native reconstruction, and Lean's `bv_decide` (bitblast → CaDiCaL → **formally verified LRAT checker in Lean**) all show: untrusted heavy search + tiny checkable certificate is the correct architecture.

6. **Verified kernels exist for HOL and are advancing for dependent types.** Candle (ITP 2022) is a fully verified HOL Light on CakeML with "an end-to-end correctness theorem that guarantees the soundness of the entire system down to the machine code that executes at runtime...the most comprehensive soundness result proved for a HOL [system]." MetaCoq ("Coq Coq Correct!", POPL 2020) is "the first implementation of a type checker for the kernel of Coq...proven correct in Coq with respect to its formal specification," motivated by the fact that "on average, one critical bug has been found every year in Coq," reframing the goal from a trusted code base to a **trusted theory base**. Lean4lean (Carneiro, TYPES 2024/2025) is a complete Lean typechecker in Lean, "around 30% slower than the C++ implementation" (Mathlib in 58.79 min vs 44.54 min), with partial correctness proofs.

## Details by Layer

### Layer 0 — Design doctrine (agreed principles, reinforced by evidence)
The user's principles are strongly supported by the 2026 evidence. De Moura's postmortem states the doctrine bluntly: *"The elaborator is untrusted by design. Soundness cannot depend on an untrusted component refusing to build a bad term,"* and that restricting metaprogramming to prevent attacks "is misguided" (an attacker can write `.olean` files or modify memory directly). The trust boundary is the kernel + export format + the arithmetic library the kernel links — and nothing else. A subtle TCB expansion the hunt revealed: even a kernel written in a proof assistant "are not immune to bugs in the Lean runtime" (the refcount and GMP exploits). **A C89 kernel with its own audited, ideally verified bignum library is therefore better positioned than a kernel hosted in a large managed runtime** — a genuine advantage of Fran's plan, provided the C code's own memory safety is treated as a first‑class soundness concern.

### Layer 1 — FOUNDATIONS (candidate logics and metatheory)

**Lean 4 type theory** (CIC + impredicative Prop + definitional proof irrelevance + quotients + eta + subsingleton elimination). Consistent (ZFC + countably many inaccessibles) but **no subject reduction, non‑transitive defeq, no Church–Rosser, decidability of defeq lost, checking can diverge** (Carneiro 2019; Abel–Coquand 2020 give the impredicative proof‑irrelevant normalization counterexample "Ω"). The trouble‑causing combination is specifically definitional proof irrelevance in an impredicative Prop that also permits large/subsingleton elimination, interacting with quotients and eta. **Verdict: do not copy Lean's exact theory into a kernel meant to have settled metatheory** — but Mathlib is written in it, so interop must confront it (Layer 3).

**Rocq/Coq pCIC + SProp.** Mature; SProp gives definitional proof irrelevance without the K‑inconsistency (Gilbert–Cockx–Sozeau–Tabareau, POPL 2019). But Coq's `critical-bugs.md` (1,260 lines, ~1,067 LOC) is a sobering catalogue whose dominant recurring root causes are: **guard/positivity checking** (many nested/mutual fixpoint bugs, numerous ones found 2025–2026 by Yann Leray, Tristan Stérin, Pierre‑Marie Pédrot, and OpenAI/Claude Opus 5); **universe / template‑polymorphism constraint tracking** (untracked constraints from ~2006 to 2019); **module subtyping** (missing substitutions, squashing/elimination‑constraint violations, some inconsistent with propext); and **conversion machines** (VM/native: arbitrary code execution on primitive floats/arrays, wrong universe constraints, a non‑bijective Coq→OCaml identifier translation that identified `True` and `False`). `coqchk` is immune to VM/native‑only bugs because it has no VM. Cumulativity, template polymorphism, and definitional‑UIP/SProp interactions recur as unsoundness sources.

**Agda (MLTT + cubical).** Predicative universes avoid Girard's paradox by default. The `--safe` flag exists because many features are individually unsound: `--type-in-type`/`--omega-in-omega` (encode Girard–Hurkens), `--injective-type-constructors` (inconsistent with excluded middle via Chung‑Kil Hur's construction), `--no-positivity-check`, `--no-termination-check`, `--sized-types` (incomplete size checks), `--guardedness` + `--sized-types` together (inductive‑coinductive inconsistency), `--large-indices` + `--without-K`. A genuine positivity soundness bug (proof of ⊥ without unsafe flags, a 2.5.3 regression) is agda/agda #3049. **Lesson: positivity, termination, and sized types are the classic soundness minefield; keep them out of the kernel or make them dead simple and conservative.**

**HOL (Isabelle/HOL, HOL Light).** Simple type theory, classical, tiny LCF‑style kernel, best soundness record in the field. Paulson: "first, naturally, Isabelle, where there has been one error every 10 years. In 2025 (last February), somebody showed how to prove false in Isabelle/HOL using normalisation by evaluation, which bypasses the proof kernel." Historical soundness issues clustered on **overloaded/circular constant definitions** (Obua 2005; Kunčar 2015), resolved foundationally by Kunčar–Popescu ("A Consistent Foundation for Isabelle/HOL", ITP 2015 / JAR 2019) via non‑overlapping definitions + a terminating definitional‑dependency relation tracked through both constants and types. Trade‑off: HOL is weaker/less convenient for large‑scale dependent mathematics than CIC, but far simpler to trust.

**Set‑theoretic systems (Metamath set.mm, Mizar, Megalodon).** Metamath is the extreme of kernel minimalism — a single substitution‑checking algorithm, foundation‑agnostic, set.mm on ZFC. Mizar uses Tarski–Grothendieck set theory with a rich declarative language. These maximize auditability and interop simplicity at the cost of automation‑friendliness and definitional convenience.

**Observational / setoid type theory (the 2022–2026 recommendation).** TTobs / CIC^obs deliver funext + propext + definitional UIP with normalization and decidable type checking *formally established in Agda*, plus quotient and Swan Id types; a 2026 LICS paper ("Definitional Proof Irrelevance Made Accessible") continues the line. This is the design point that most closely matches the user's checklist: consistency, decidable checking, subject reduction, transitive defeq, a known consistency proof, *and* the extensionality principles practical mathematics wants.

**Recommendation (Foundations).**
- **Primary:** adopt an **observational/setoid dependent type theory (TTobs/CIC^obs family)** with a **predicative** universe hierarchy (avoid impredicative Prop's Ω traps) and classical axioms (choice, EM, propext) added *as reduction‑blocking axioms*, HOL‑style — so reduction stays normalizing and the axioms only affect provability, not conversion. This gives every property on the user's list with a machine‑checked metatheory.
- **Conservative fallback:** if the observational theory is judged too young for a 1.0, adopt **predicative CIC with SProp‑style definitional proof irrelevance (no impredicative Prop), no cumulativity by default**, and explicitly conservative positivity/termination — closer to MetaCoq‑verified ground.
- **Interop‑only track:** keep a deliberately weak **HOL‑style** or **Metamath‑style** kernel as one of the independent checkers for maximal auditability.
- **Feature‑by‑feature rulings:** never combine impredicative Prop + large elimination + definitional proof irrelevance (Abel–Coquand Ω); avoid kernel cumulativity (Coq's variance/subtyping bug cluster); prefer derived/observational quotients over a primitive with its own reduction rule; make nested/mutual inductives the most scrutinized part of the spec (where #14576 and most Coq guard bugs live); admit eta only where the metatheory paper covers it.

### Layer 2 — KERNEL IMPLEMENTATIONS

**Sizes/architectures.** HOL Light `fusion.ml` ~396–430 lines OCaml (verified in Candle). Metamath: `mmverify.py` ~350 lines Python; `checkmm.cpp` a single self‑contained C++ file (exact LOC unconfirmed); `metamath-knife` a large multithreaded Rust project (verifies set.mm in well under a second). Lean 4 C++ kernel (`src/kernel/`: `type_checker.cpp`, `expr.cpp`, inductive/quot/level): exact LOC **unconfirmed** (estimated low‑thousands to <10k; flagged uncertain). It uses **intrinsic per‑Expr hash + maximal sharing (`shareCommon`, "hash‑consing after‑the‑fact")**, **per‑role is_def_eq/whnf/infer caches**, and **special kernel literal support for Nat/String backed by GMP**. `nanoda_lib` (author **ammkrn**) is a "small, audit‑friendly" independent Rust Lean kernel reading the lean4export NDJSON format, with locally‑nameless binding and optional Nat/String literals (exact LOC unconfirmed). `lean4lean` (Carneiro) is a complete Lean kernel in Lean, ~30% slower than C++, usable on all of Mathlib. `coqchk` is Coq's standalone re‑verifier (no VM → immune to VM/native bugs). Isabelle/Pure was formalized with an executable proof‑term checker by Nipkow–Roßkopf (CADE‑28 2021); the inference system is ~300 readable LOC, and they deliberately chose *certificate checking* over verifying the optimized multithreaded ML kernel, which "has once lead to a soundness issue."

**Which performance techniques are safe vs risky in a kernel.**
- *Safe/recommended:* hash‑consing / maximal term sharing (pure, well‑understood); de Bruijn indices; a simple arena allocator; whnf/def‑eq caches **only with a complete, order‑independent key** — Lean #14806 was precisely an *order‑dependent* is_def_eq cache.
- *Risky — keep out of the trusted core or isolate behind re‑checking:* multiple reduction machines (Coq's VM/native are the single largest bug source); NbE with aggressive optimizations (Isabelle's 2025 NbE bypass); kernel literal arithmetic via a large external bignum (the GMP 6.1.2 exploit) — hence Lean's plan to ship GMP *and* `mpn` builds *and* eventually **a simple verified arbitrary‑precision arithmetic package**.
- *Bounds:* Lean added #14849 to **bound the size of Nat numerals the kernel computes** after a multi‑gigabyte adversarial numeral. A greenfield kernel should bound literal sizes and recursion depth from day one.

**C implementation experience (for Fran).** (a) Write/verify your own bignum, or use two independent ones and cross‑check (Lean's GMP‑vs‑mpn plan). (b) Arena/region allocation with one intrinsic hash field per node enables cheap hash‑consing and pointer‑equality fast paths — but the fast path must be *sound* (an α‑conversion pointer‑equality bug is exactly what Paulson recounts introducing in LCF decades ago). (c) Bound all kernel‑side computation. (d) Make the def‑eq cache key canonical/order‑independent. (e) Keep exactly one reduction strategy in the trusted kernel.

**Recommendation (Kernel).** Primary kernel in **C89**: de Bruijn indices, arena allocation, hash‑consing with intrinsic hashes, one whnf/def‑eq algorithm with an order‑independent cache, its **own audited (later verified) bignum**, bounded numeral computation, and a hard rule that nested/mutual inductive handling gets a from‑first‑principles model check (mirror Breitner's `lean-inductive-models`, which "proves that an inductive type, including its recursors and reduction rules, can be modelled from first principles"). Ship a **second kernel in a different language** from day one, and adopt a **Lean‑Kernel‑Arena‑style** open registry of independent kernels with a **`--paranoid` unanimous‑agreement mode**.

### Layer 3 — PROOF CERTIFICATE / EXPORT FORMAT AND INTEROP

**State of the art.** Lean's `lean4export` emits a plain‑text/NDJSON declaration format in the kernel language, consumed by external checkers. Community design notes: the exporter is *not trusted*; the export must use **back‑references for Expr/Level/Name to avoid exponential blowup**; def/theorem/opaque and reducibility hints affect only performance, not kernel semantics. `comparator` is the "gold standard": it cleanly separates *statement* from *proof*, sandboxes the check, and dispatches to external kernels with an explicit `permitted_axioms` list (`propext`, `Quot.sound`, `Classical.choice`). Dedukti/Lambdapi (λΠ‑calculus modulo rewriting) is the general interop framework (HOL→Dedukti via Holide, Coq via CoqInE, exports to Lean/Matita/PVS/OpenTheory); OpenTheory is the HOL‑family interchange; MMT/OMDoc is the meta‑framework.

**Importing Mathlib into a different/cleaner kernel.**
- *Feasible in principle:* lean4export already exports Mathlib's kernel terms; a checker with the *same* theory can recheck them (nanoda, lean4lean do). Gebner's textual‑export importer reconstructed Mathlib declarations (as axioms) in ~6 min / 13.5 GB RAM.
- *Hard pitfalls with a **different** theory:* Mathlib's terms rely on Lean's exact defeq, **quotients**, **definitional proof irrelevance**, **impredicative Prop**, and **eta** — precisely what a cleaner observational/predicative kernel changes. Terms that typecheck only because of Lean's proof irrelevance or its (non‑transitive) defeq may not check under a different conversion. A full semantic import is *not* free; expect to (a) run a dedicated "Lean‑compat" checker that accepts Lean's theory, (b) translate through Dedukti with explicit encodings of the problematic principles, or (c) re‑elaborate/re‑prove. The export also carries **no tactics or notation** — fine for checking, not for reading (hence the pretty‑printer requirement).

**Recommendation (Certificate).** Specify a **stable, versioned, tool‑independent certificate format** with complete back‑referencing; explicit universe levels; an explicit **closed axiom manifest** per declaration (comparator‑style); and content hashes for reproducibility (noting the Lean Zulip caution that a cryptographic hash then joins the TCB). Provide a **Lean‑compat import path** (accept lean4export, check under a Lean‑faithful kernel) *and* a **native path** for proofs authored in your own theory. Treat Dedukti as the heterogeneous‑interop escape hatch. **Do not make Mathlib import a 1.0 soundness dependency** — make it an additional corroborating check.

### Layer 4 — ELABORATOR SPECIFICATION

**State of the art / core lesson.** Lean's most cited flaw for a greenfield system is that **the elaborator, in practice, defines the language** — large, user‑extensible, unspecified, making independent reimplementation near‑impossible — even though the elaborator is *untrusted*. The academic path to a *specified, deterministic* elaborator is **bidirectional typing**: Lennon‑Bertrand's "Complete Bidirectional Typing for the Calculus of Inductive Constructions" (ITP 2021), formalized in MetaCoq, introduces *constrained inference* for computation in types and proves completeness vs. the undirected system; his thesis extends this to PCUIC and underpins the MetaCoq correctness effort. Higher‑order unification is undecidable, so real elaborators restrict to **Miller/higher‑order pattern unification** (decidable, most‑general solutions). Lean elaboration innovations worth adopting selectively: **tabled typeclass resolution** (Selsam–Ullrich–de Moura 2020, solving the diamond and cycle problems), **elaboration postponement**, and **hygienic macro expansion**. Idris 2 (Quantitative Type Theory, elaboration reflection), Agda, Matita, and Andromeda (an LCF‑style nucleus where the elaborator/tactics are untrusted and the nucleus checks judgments) are the other reference points.

**Recommendation (Elaborator).**
- **Specify the elaborator on paper before building it**, as a **bidirectional** system (infer/check/constrained‑infer) in the Lennon‑Bertrand style, targeting your kernel's term language; make it **deterministic** given a fixed library state so a second implementation is feasible and proofs stay stable across versions.
- Restrict unification in the specified core to the **higher‑order pattern (Miller) fragment**; allow heuristic extensions only as *untrusted* elaboration that still emits kernel‑checkable terms.
- Adopt **tabled typeclass resolution** and **hygienic macros**, but keep them outside the trusted core and inside the *specified* elaborator boundary.
- Publish a conformance test suite so alternative elaborators can be validated — the antidote to "the elaborator is the language."

### Layer 5 — AUTOMATION WITH CERTIFICATES

**State of the art.** The Sledgehammer model (Isabelle): call external ATP/SMT solvers as untrusted oracles, then **reconstruct** a kernel‑checkable proof. Concrete pipelines: (a) **Alethe** generic SMT proof format (veriT, cvc5), reconstructed in Isabelle/HOL and (via SMTCoq) in Coq; Carcara/Ethos are fast Alethe/Eunoia checkers. (b) **lean‑smt** (Barbosa et al.) translates Lean goals to SMT (via lean‑auto), runs cvc5, and reconstructs native Lean proofs — also usable as a standalone SMT‑LIB checker with a smaller trusted core. (c) **bv_decide / LeanSAT**: bitblast → CaDiCaL → **formally verified LRAT checker in Lean** (now `Std.Tactic.BVDecide`); `lrat-catcher` scales this via reflection and composes cube‑and‑conquer runs, tracking exactly which axioms (the three standard + one `native_decide` per reflected check) each theorem uses. (d) **grind**: "all heavy search happens outside Lean; the certificate is replayed and verified inside Lean."

**Best practice for keeping automation fully untrusted.** Every tool must output a certificate the kernel (or a small verified checker) replays: SMT proof terms (Alethe), UNSAT certificates (LRAT/DRAT with a verified checker), or explicit proof terms. Never trust the solver's yes/no. Track the axiom footprint of every reconstructed proof. Be explicit about reflection's TCB cost — bv_decide's `ofReduceBool`/native compilation adds the compiler to the TCB, so prefer kernel‑checked replay over native reflection, or offer both modes (as lrat‑catcher does).

**Recommendation (Automation).** Mandate a **certificate contract**: no tactic, SMT bridge, SAT bridge, or AI prover may assert a theorem except by producing a kernel‑checkable object. Standardize on **Alethe (or a successor) for SMT** and **LRAT for SAT/bitvector**, each with a **verified checker** in your own system. Provide a Sledgehammer‑style relevance filter + reconstruction front‑end for AI provers. Keep two replay modes (kernel‑only and reflected) and always report the axiom footprint.

### Layer 6 — DECLARATIVE SURFACE SYNTAX

**State of the art.** Mizar (Tarski–Grothendieck, declarative, huge library) is the progenitor of readable formal proof. Isabelle/**Isar** is the "human‑readable structured proof language" descendant. **Naproche/ForTheL** (now Isabelle/Naproche; Naproche‑ZF) checks controlled‑natural‑language mathematics close to ordinary English, backed by external ATPs, and can emit Lean; the EuroProofNet CNL white paper surveys the space. Lean‑side readability efforts: **Lean Verbose** (structured natural‑language tactics) and **Waterproof** (Coq, educational structured proofs). Consensus: term/programming‑style proofs are unreadable to working mathematicians; explicit declarative structure is what makes proofs auditable — Paulson notes a *legible* proof "can even reveal incorrect definitions, since the proof steps won't follow the expected line of reasoning."

**Recommendation (Surface).** Adopt a **declarative, Isar/Mizar‑style surface language** as the primary human‑facing syntax: explicit intermediate goals, `have/show/obtain`‑style steps, block structure, readable justifications. This is the right substrate for the AI‑writes/human‑reviews workflow: the reviewer reads a structured argument, not a proof term. Offer a controlled‑natural‑language layer (ForTheL‑inspired) as an optional front‑end. The surface elaborates (via the specified Layer‑4 elaborator) to kernel certificates, so readability never trades against soundness.

### Layer 7 — TESTING AND BUG HUNTING

**State of the art.** Techniques with published use on proof assistants/type checkers: **differential testing** (the point of Metamath's five verifiers and Lean's `--paranoid`); **property‑based / coverage‑guided testing** (QuickChick, foundational PBT in Coq); **automatic test‑case reduction / bug minimizers** (Coq bug minimizer, delta‑debugging); **mutation/fault injection**; and **AI‑assisted adversarial hunting** (the 2026 OpenAI‑model Lean hunt). The **Lean FRO Year‑4 "Trust" roadmap** (Sept 2026–Feb 2027) is the template: `lake check` (export + recheck with the official kernel + comparator prelude checks), `lake check <kernel>`, and **`lake check --paranoid`** (recheck with *all* bundled kernels — leanchecker‑paranoid, lean4lean, nanoda, con‑leche — accept only if all agree), plus a `lake build` mode that *skips* kernel checks so independent checking becomes the explicit default habit. De Moura's post‑#14576 hardening: kernel‑invariant checks; `lean-inductive-models`; two bignum backends + a planned verified one; bounded numerals; new GitHub tags `soundness` / `runtime-soundness`.

**Recommendation (Testing) — build in from 1.0:**
1. **Differential checking** across ≥2 kernels on every proof (`--paranoid`; accept only on unanimous agreement).
2. A **regression corpus of every known soundness bug** — seed directly from Coq's `critical-bugs.md` (guard/positivity, universe/template polymorphism, module subtyping, conversion machines, primitive projections, deserialization), Lean #14576 and the bug‑hunt PRs (#14613/#14616/#14806/#14807/#14838/#14849), Agda #3049 and the `--safe` feature list, and the Isabelle overloaded‑definition and NbE cases. Each entry is a test the kernel must *reject*.
3. **Mutation testing of valid proofs** (perturb checked proofs; the kernel must reject).
4. **Fuzzing against metatheoretic properties** (generate terms; check subject reduction, confluence, decidability‑of‑defeq invariants — feasible precisely because the chosen theory makes these *true*).
5. **Adversarial AI bounty** for a proof of `False` (mirror the OpenAI hunt), adjudicated by export‑and‑recheck + comparator.
6. **Bounded computation and canonical cache keys enforced by tests.**

### Layer 8 — VERIFIED KERNELS

**State of the art (2026).** **Candle** (Abrahamsson–Myreen–Kumar–Sewell, ITP 2022; JAR 2025): a fully verified HOL Light clone on CakeML with "an end-to-end correctness theorem that guarantees the soundness of the entire system down to the machine code that executes at runtime...every exported fact produced by this machine-code program is valid in higher-order logic...the most comprehensive soundness result proved for a HOL [system]." **MetaCoq/MetaRocq** (Sozeau et al., "Coq Coq Correct!", POPL 2020; JACM 2024): "the first implementation of a type checker for the kernel of Coq (without the module system and template polymorphism), which is proven correct in Coq with respect to its formal specification," motivated by "on average, one critical bug has been found every year in Coq," shifting from a trusted code base to a **trusted theory base**. **Lean4lean** (Carneiro, TYPES 2024/2025): first complete Lean typechecker besides the C++ one, ~30% slower, with an abstract formalization of Lean's type theory and partial correctness proofs; it "does not need to mirror the official kernel line by line." **con-leche** (Breitner): compromises on the checker to obtain a *direct model‑based consistency proof* not needing Lean's hardest metatheoretic properties. **MCTT** (Jang–Gaulin–Hu–Pientka, ICFP 2025) is a verified kernel for a Martin‑Löf proof assistant. The 2025 survey "What does it take to certify a conversion checker?" notes that for dependent type theory a fully certified kernel is "still missing, despite 30 years of efforts," even as HOL has had Candle for years.

**Recommendation (Verified kernel).** Make it a **staged 1.x goal, not a 1.0 blocker.** Because Layer 1 chose a theory with a *machine‑checked metatheory* (observational/setoid, proved in Agda) or well‑trodden predicative CIC (MetaCoq territory), the verification target is far more tractable than verifying Lean's theory. Stage it: (a) 1.0 ships two independent naive kernels + differential checking; (b) verify the conversion checker against the paper spec (the "What does it take to certify a conversion checker?" agenda); (c) extend to inductives (the hardest part — where lean4lean's consistency proof does *not yet* reach and where #14576 lived); (d) close the runtime/compiler gap via a Candle‑style end‑to‑end machine‑code proof or de Moura's AI‑auto‑translate‑and‑cross‑run proposal.

### Layer 9 — LIBRARY AND STATEMENT AUDITING

**State of the art.** The central 2026 development is **Palomar** (Tao's announcement 18 Aug 2026; incubated by ICARM + Lean FRO; advisory board incl. Avigad, Ballard, Kra, Vakil, Venkatesh, Morrison; four technical maintainers Tao, Ballard, Guillen, de Dios Pont). It is "a registry of Lean‑verified mathematical results" — a preprint‑server analogue recording an **immutable repo snapshot**, the exact toolchain, and pinned dependencies, passing **three automated gates**: (1) **comparator** mechanically verifies the proof proves the *recorded statement* against a specified Mathlib using only permitted axioms, rechecking through **both Lean's kernel and the independent NanoDa kernel**; (2) a **language model judges whether the formal statement is a fair rendering of the informal claim** and meets a research‑interest floor; (3) a disclosure/metadata check. Per Palomar's About page, "Palomar caps the size of the formal statement at 1,000 lines and 100 KiB. Imports are restricted to Lean core and pinned allowlisted libraries" so the LLM can audit the definitions actually reached. It explicitly does *not* referee mathematics and does not re‑run entries against later toolchains. Mathlib itself relies on human review + linters + `assert_not_exists`/consistency tooling (Grove). **Formal Abstracts** (Hales) is the antecedent vision of machine‑checkable theorem statements. The recurring unsolvable‑by‑machine problem: **does the formal statement mean what the mathematician intended** (degenerate cases, wrong definitions).

**Recommendation (Auditing).** Ship a **Palomar‑style registry** as part of the system: immutable snapshots; strict separation of *statement* (audited by humans/LLMs) from *proof* (checked by kernels); a mandatory **axiom manifest**; a statement‑size cap to keep statements auditable; LLM‑ and human‑assisted **definition audits** for degenerate‑case correctness; and pinned, reproducible toolchain records. Adopt the comparator discipline (clean statement/proof separation, sandboxed checking, explicit permitted axioms) at the tooling layer. Because AI will author many proofs, the statement‑audit and disclosure gates are load‑bearing, not optional.

## Recommendations (staged, with decision thresholds)

**Stage 0 — Specification (before any kernel code).**
- Fix the logic on paper: choose the **observational/setoid predicative theory** (primary) or **predicative CIC + SProp‑style proof irrelevance, no cumulativity** (fallback). *Prefer the fallback if* the observational theory's inductive‑type metatheory is not yet published at the maturity you need, or if Mathlib‑import fidelity outranks metatheoretic cleanliness for your first users.
- Write the full typing + conversion spec, the **bidirectional elaborator spec**, and the **certificate format spec** (back‑references + axiom manifest) — all versioned.

**Stage 1 — Two naive kernels + export + differential checking (the 1.0 core).**
- Primary kernel in **C89** with its own bignum, bounded numerals, de Bruijn, hash‑consing, one conversion algorithm, order‑independent caches, from‑first‑principles inductive checks.
- Second kernel in a different language; `--paranoid` unanimous‑agreement mode.
- Stable certificate format + pretty‑printer; comparator‑style statement/proof separation with permitted‑axiom lists.
- Regression corpus seeded from Coq `critical-bugs.md`, Lean #14576 + bug‑hunt PRs, Agda `--safe`/#3049, Isabelle overloading/NbE. *Proceed when* every historical bug in the corpus is rejected by both kernels.

**Stage 2 — Untrusted automation + declarative surface.**
- Certificate contract for all tactics/SMT/SAT/AI; Alethe + verified‑LRAT checkers; Sledgehammer‑style reconstruction.
- Isar/Mizar‑style declarative surface + optional ForTheL CNL front‑end; specified deterministic elaboration to certificates.

**Stage 3 — Continuous adversarial testing + registry.**
- Mutation testing, property/metatheory fuzzing, AI adversarial bounty for `False`, export‑and‑recheck as the default habit.
- Palomar‑style registry with statement caps, axiom manifests, LLM+human definition audits, pinned toolchains.

**Stage 4 — Verified kernel (1.x, not 1.0).**
- Verify conversion checker vs. spec → inductives → end‑to‑end/runtime gap. *Invest heavily when* the theory's metatheory is machine‑checked and stable, and the differential‑checking + bounty infrastructure has run long enough to have surfaced the "easy" implementation bugs.

## Caveats and Open Risks
- **Observational type theory is young in production terms.** Its metatheory is machine‑checked (Agda) and very attractive, but no Mathlib‑scale library is yet built on it; betting a maximalist 1.0 on it carries adoption/ecosystem risk. The predicative‑CIC fallback is safer but sacrifices some extensionality convenience. This is the single biggest open design risk.
- **Mathlib import into a cleaner kernel is not free.** Lean's terms depend on quotients, definitional proof irrelevance, impredicative Prop, and its non‑transitive defeq; a cleaner theory may reject or need to re‑encode them. Treat import as corroboration, not a soundness dependency.
- **Several LOC/architecture figures are unconfirmed.** Exact line counts for the Lean C++ kernel, nanoda_lib, and checkmm.cpp could not be verified from primary sources within budget; the HOL Light (~400) and mmverify.py (~350) figures are well‑sourced. Treat kernel‑size targets as order‑of‑magnitude guidance.
- **The TCB is wider than "the kernel."** The 2026 hunt showed runtime (refcount overflow) and external‑library (GMP 6.1.2) exploits bypass even correct kernel logic. A C89 kernel with an audited/verified in‑house bignum and bounded computation mitigates this better than a managed‑runtime host — but the C code's own memory safety becomes a first‑class soundness concern (fuzz it; consider a verified or Rust second kernel).
- **The statement–intent gap is unclosable by machines alone.** No kernel or registry guarantees the formal statement means the intended mathematics; the Palomar model explicitly relies on human + LLM judgement and disclosure. Budget for sustained human review as AI authors more proofs.
- **AI adversaries scale.** The Collatz episode shows AI can both find kernel bugs and (potentially) target them. The defensive posture — multiple kernels, export‑and‑recheck, bounty, hardened invariants, verified arithmetic — must be permanent infrastructure, not a one‑time audit.
- **Evidence thinness noted honestly:** the claim that verifying an observational‑theory kernel is *easier* than verifying Lean's is inferential (based on the metatheory being machine‑checked and on MetaCoq/con‑leche experience), not yet demonstrated by a completed verified observational kernel as of September 2026 AD.
