dispensator

Ansa: derivare -> destinatio -> actio -> componere

The loop of a ludus program: derive (derivare), target (destinatio), act (actio), recompose. After EVERY dispatched event it rebuilds the component tree by calling the program's Componere function over the state (the island and motus), into one of two ping-pong arenas so the previous tree stays valid while the next is built; painting and rasterizing happen once per frame, outside it. It owns hover (which component is under the pointer, deriving entered/left), focus and the focus stack (kept in the island, so a restore restores them), and the quiet point: when motion settles it flushes motion into the island, and an application's gesture likewise after that gesture's own interval. dispensator_pulsare feeds it time with no input, so quiet and recomposition happen when nothing arrives, and dispensator_finire flushes whatever is pending at exit; before 2026-10-05 nothing did, and pictor never noticed because a stroke ends on mouse-up. Since vicus mounts several applications in one tree, the loop works in scopes and branches: a component's action resolves in that component's own scope, so a click lands in the right copy of an application whichever pane has focus, while focus, capture and Tab cycling resolve inside the focused pane and focus is stored in its branch. For the dismissal system it gained one pair of hooks, before an event is sent and after an action has consumed it. A notary option records every raw event it receives, with the component it reached and the point in that component's space, for replay (eventus_notata_scribere_stml). Pure (nexus purus): the whole loop runs and is tested with no window. Used by pictor, scriba, terminale and vicus.
