json

Parser et aedificator JSON: reading, building and writing JSON, in an arena

The house's JSON library: a strict reader, a mutable tree, and a writer, all allocating in a Piscina (arena) so a whole document is freed by emptying one arena. It is one of the most used libraries in the tree: json_legere has 114 uses in 17 files (./silva/nexus.sh json_legere, 2026-10-02), above all the ledger and its MCP residents (gesta/), the HTTP layer (manus), silex, the webview bridge (internuntius) and the message carrier (tabellarius). So most of what arrives from a client passes through it.

Files: include/json.h (397 lines), lib/json.c (2,490), lib/json.worklog.md, tests in probationes/probatio_json.c. Depends on piscina, chorda, xar, internamentum, chorda_aedificator, utf8.

Capabilities

Reading

  • Strict RFC 8259 by default, with no lenient mode: the whole input is one value (anything after the root is refused, so 1 2 or a lost newline gluing two log lines together is an error); no trailing commas, comments or leading zeros; only the legal escapes; raw control characters refused.
  • Numbers that refuse instead of lying: integers are exact s64, and anything outside −2⁶³…2⁶³−1 is an error, never silently wrapped or rounded; floats are f64, with 1e400 refused and underflow accepted.
  • Strings are valid UTF-8: surrogate pairs combine into four-byte UTF-8, lone surrogates are refused, and raw bytes are checked (overlong forms, encoded surrogates and truncated sequences are refused).
  • Duplicate keys are refused ("Clavis duplicata"), so an event with two values for one field cannot pass as valid.
  • Errors you can act on: line and column (counted in characters, not bytes), and the true cause when a lexer error sits inside a container ("Clavis chorda expectata: Chorda non terminata").
  • A depth limit of 256 nested containers, so hostile input cannot exhaust the stack.

Access

  • Type checks and extraction with zero defaults (json_ad_integer returns 0 for a missing or wrong-typed value).
  • Access with an explicit default: json_capere_chorda / _integer / _boolean (objectum, clavis, ordinarium), which never fail.
  • A dotted path, json_via(radix, "a.b.0.c"): a numeric segment indexes an array, any other names a key.
  • Iteration over objects in insertion order.

Building and writing

  • A mutable tree: create values, add to arrays, put keys into objects (putting an existing key overwrites it in place).
  • Compact and pretty output, into a new string or into an existing ChordaAedificator.
  • Floats written in the shortest form that reads back exactly (0.1, not 0.10000000000000001), with .0 added when the text would otherwise read back as an integer; NaN and infinities are written as null.

What it deliberately does not do

  • No streaming or event (SAX) interface: the whole document is built as a tree.
  • No lenient modes (comments, JSON5, trailing commas, NaN in input).
  • No JSON Pointer (RFC 6901): the dotted path cannot reach a key that contains a dot; use json_objectum_capere for those.
  • No unsigned 64-bit integers above 2⁶³−1.
  • The builder does not detect cycles, and the writer does not validate UTF-8 in strings it was given (both documented in json.h).

The nearest relatives in spirit are parson (C89, a mutable tree, a dotted path, duplicates refused) and jansson (strict, good errors). What sets this one apart is the combination of arena allocation, which fits the house's piscina discipline and makes freeing a document one call, and a strictness chosen for logs that are the record of truth: exact integers, refused duplicates, one value per input. For raw speed the C++ simdjson and the C yyjson are in another class, reported in gigabytes per second; nothing in the house needs that today.

Performance

Measured 2026-10-02 on the ledger's own journal (gesta/annales/tabularium.jsonl: 4,318 lines, 3.5 MB, one JSON object per line, all of which parse), five passes, one arena emptied after each line, -O2, Apple silicon. Python's C-accelerated json module on the same lines and machine, as a familiar yardstick:

parsewrite (compact)
rhubarb json354 MB/s379 MB/s
Python json219 MB/s198 MB/s

Two costs that grow faster than the input, both in the audit below: the duplicate-key check during parsing, and key lookup, are linear per key, so quadratic per object. Ordinary house objects have a handful of keys and never notice.

Audit, 2026-10-02

Filed in the ledger as park …XW32T. This audit looked where the September audit (below, in the timeline) did not: memory over time, cost on large inputs, the newer json_via, failure paths. Each finding marked confirmed was reproduced by a probe compiled outside the library (nothing in lib/ was changed); by reading means found in the source, not reproduced. None is fixed yet.

FindingSeverityEvidencePossible fix
Keys are interned globally and never freed. Every key of every parsed object goes into the process-wide intern table, which outlives the arena; and a lookup of an absent key interns it too. medium for the residents, which parse client input for days confirmed: 10,000 parses of one-key objects with unique keys, arena emptied after each, left 10,000 entries in the table; 1,000 failed lookups added 1,000 more. Lookups: check chorda_est_internata first; a key never interned cannot be in any object, so answer "absent" without inserting. Parsing: a table per document (in its arena), or accept the cost and document it.
Quadratic cost per object. The duplicate-key check during parsing scans all earlier keys; lookup and json_objectum_ponere scan linearly. high: seen in practice (below), and a hostile client can send one large object confirmed: one object with 5,000 keys parses in 0.036 s, 10,000 in 0.143 s, 20,000 in 0.565 s (each doubling costs four times more; 200,000 keys would take about a minute).
Seen in practice the same day: Lapide's feature request 025 (../lapide-v2/docs/briar-feedback/). Indexing 14,628 OCR word ids as one object's keys took 3.1 s against 1.2 s with tabula_dispersa; the profile was dominated by json_objectum_capere_chorda → xar_obtinere.		 Keys are already interned pointers, so an index only hashes a pointer: past a small number of keys (8–16), build a pointer → slot table in the arena, keeping the xar for insertion order. That fixes lookup, insertion and the duplicate check at once. Meanwhile, say in json.h that objects are for small records and tabula_dispersa for maps. A cap on keys per object, like the depth cap, would also bound a hostile input. If tabula_dispersa is used instead of a pointer table, mind that it silently refuses an empty key (ledger note …6KEQPR).
json_via can wrap an array index. The bounds check computes numerus − digit, which underflows in the house's unsigned i32 when the digit exceeds the element count; the index then wraps past 2³². low: needs an absurd path, but paths can come from input confirmed: on {"a":["zero"]}, json_via(radix, "a.4294967296") returns "zero". Accumulate the index in a 64-bit unsigned and compare with the count once, or refuse more digits than the count has.
Every string is copied twice. The token is copied out of the input, then unescaped into a second copy, even when it has no escapes; numbers are copied twice too (token, then a NUL-terminated copy for strtod). low: performance only by reading (_parser_token_valor then _unescape_chorda). Unescape straight from the input slice; when a string has no backslash, one copy suffices.
Allocation failure can lose data silently. If xar_addere fails while parsing, the key/value pair is dropped and the parse still reports success; a failed string allocation returns failure with an empty message. low: only under memory exhaustion by reading (_parse_objectum, json_tabulatum_addere). Treat a failed xar_addere as "Allocatio fallita".

Already known and accepted (json.worklog.md, September): strtod depends on the C locale, which the house never sets; the builder does not detect cycles; the writer does not validate UTF-8. The September iscntrl issue in the string escaper has since been fixed.
