volumen

volumen (rotulus documentorum): a whole document in one SQLite file, with an event log as its truth

A volumen (a scroll of documents) is one SQLite file that holds a whole document, so copying the file copies the document. Inside it the truth is an append-only log of events; file contents are stored once each, addressed by their hash; and the list of "which path holds which content" is only a projection, which can be rebuilt from the other two. Corrupting the projection therefore never loses data. It began in August 2026 as the store for silex projects and has since become the place where every house application keeps its state: one volume per application.

Files: include/volumen.h (226 lines), lib/volumen.c (840), lib/volumen.worklog.md, tests in probationes/probatio_volumen.c. It sits on scrinium (the house's SQLite wrapper) and sigillum (SHA-256). Group: Records and storage. The header still says the name is not sealed.

How it works

Three tables

TableHoldsRole
actasequence number, time, kind (genus), data (text)The truth. Rows are only ever appended. The sequence number is SQLite's own autoincrement, and the time is stamped by SQL when the row is inserted, so the library calls no clock.
massaeSHA-256 hash (hex), content (blob)Contents, stored once. The hash is the primary key and inserts are "insert or ignore", so the same bytes written twice occupy one row. Nothing here is ever deleted.
plagulaepath, hash, origin, time The manifest, a projection. One row per path, pointing at a row of massae. It is what a reader consults, and it can be reconstructed from acta.

Writing and removing a file

volumen_plagulam_condere(vol, path, content, origin) hashes the content and then does three things in one transaction: stores the blob if it is not there already, appends an act of kind plagula-condita whose data is a small JSON object (path, hash, origin), and writes the manifest row, replacing any earlier row for that path. If any step fails the whole transaction is rolled back, so the log and the manifest cannot disagree. The origin is a free label saying where the content came from (vendicata:lib/chorda.c for a vendored file, genita for a generated one).

volumen_plagulam_removere appends a plagula-remota act and deletes the manifest row. The blob stays, because earlier points in the history still refer to it. Removing a path that is already absent succeeds.

Reading

volumen_plagulam_promere looks the path up in the manifest and returns the blob it points at. It reports "not found" through a separate flag, because an empty file is a legitimate content and must not look like a missing one. volumen_plagulas_enumerare returns the whole manifest in path order.

The log, and travelling back along it

A client can append acts of its own with volumen_actum_appendere(vol, kind, data) and read them back with volumen_acta_legere(vol, after_seq), which returns every act after a given sequence number. That "after N" shape was chosen because it serves two readers at once: a program folding the log into its state, and a future replication that asks for what it has not seen. One consequence to know: the volume's own acts and every client's acts share one sequence, so a client's sequence numbers are not contiguous, and its first act is not number 1.

volumen_plicam_ad(vol, seq) rebuilds the manifest as it stood at any point, by replaying the plagula-condita and plagula-remota acts up to that sequence number. A file removed later reappears in an earlier fold. The test suite pins the property that makes the design honest: the fold of the whole log must equal the stored manifest, which is the proof that the manifest really is a projection and could be thrown away.

Blobs without a path

volumen_massam_condere stores bare content and returns its hash; volumen_massam_promere fetches it by hash. The doctrine in the worklog is that a blob is content, not an event: what the content is used for is recorded in an act that names the hash. This is how large things are kept out of the log: a pasted image in pictor, a checkpoint of a drawing, an image card in mensa.

Transactions

Each operation normally runs in its own transaction. To commit several files atomically, a caller opens one itself (volumen_transactionem_incipere, _committere, _revolvere); while it is open the file operations skip their own, since SQLite does not nest transactions. The database is opened through scrinium with write-ahead logging, a five-second busy timeout and foreign keys on. The schema is a list of migrations that is only ever appended to.

Scratch volumes

volumen_temporarium(piscina, prefix) creates a volume under /tmp that is deleted when it is closed. It exists because of a measured accident (2026-08-13): a smoke test of the laboratorium app used the app's fixed path, and after one day Fran's real volume held 42 greetings and 21 experiments that nobody had written. Worse than the litter, such a test is not repeatable, because its counts grow with every run.

The file is named /tmp/<prefix>-N.volumen with the first free N from 1 to 100, deliberately not a random name: a test that forgets to close leaves its file behind under a name that says whose it is, and the leftovers can be counted. The other side of that choice showed in October, when two tests that never closed their volumes used up all hundred names and turned a gate red on code nobody had touched. A test must close what it opens.

What lives in a volume today

The library gives paths and kinds no meaning; the conventions belong to its clients. An application's volume typically holds:

ClientWhat it keepsWhere
silexthe files of a project, vendored or generated, and its commits as points in the log manifest paths; acts
historiaa document as a log of acts with branches, an undo cursor and checkpoints (pictor's drawings, scriba's pages)acts of kind <namespace>/<kind>; a manifest entry <namespace>/documentum; checkpoints at <namespace>/checkpoint/<seq>, their bytes as blobs
conservatiothe persistent fields of each mounted widgetmanifest paths status/<key>
vicusthe layout of tabs and panes (configuration, overwritten)manifest path vicus/latera
scriba_liberthe index of pages and which page each view showsscriba/paginae, scriba/visus/<id>
mensathinkboards: cards as acts, pasted images as blobsacts; blobs
mensuraa run's measurements, moved in from a plain journal at the endacts

Namespaces are what let several documents share one file: historia prefixes its kinds and paths with the document's name and reads only its own. That was added on 2026-10-05 when Fran chose one volume for the whole of vicus, so that every tab's document, the layout and the widget state travel together in a single file.

What it does not do

  • No garbage collection. A blob is never deleted, even when no manifest row points at it, because the history may. A volume only grows.
  • No replication yet. The log reads were shaped for it, but nothing ships acts between two volumes.
  • No kinds, custody or persons. The header names these as what will live here one day, and says the library grows only when something pulls on it.
  • No meaning for paths or acts. It cannot tell a drawing from a page; a client that opens the wrong namespace gets what it asked for.
