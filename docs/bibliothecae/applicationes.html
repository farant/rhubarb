Applicationes

The four applications in apps/

The libraries are the house's parts; these are where the parts meet a person. Three of the four are vitrea apps (a web page as the face, C89 as the body) and one is built on ludus, the native second-generation UI. All four share two habits. Each binary carries a headless smoke mode (-fumus) that runs the real thing without anyone watching and exits with numbers, so an app can be gated like a library. And each app file mostly wires rather than does: the real work lives in lib/, where the root test suite can reach it.

forum

The writing place: a window onto the world of writings

forum is where Fran writes: articles, short posts (pipata), threads and replies, with statuses and revisions, all stored in the ledger itself. The app is a vitrea window that talks to the ledger's resident daemon (tabulariumd) over a TCP connection per request, starting the daemon if it is absent; its C side exposes a set of RPC methods (read, send, save an article, set a status, edit, delete) and every write is recorded with the actor fran, while Claude writes to the same world through the MCP tools, with a signature. Interview, spec and the first four phases were done in one day (2026-07-22), and it was lived in from that day.

It has grown into the house's reading-and-writing desk. It reads books of numbered claims (sententiae) and tables of contents (capitula), draws the census of the house's semantic library as a graph (charta), and can serve itself to a phone: a second process runs the same methods over HTTP (vitrea_servus), and a QR code carries the address (rete finds the candidates). It wears speculum (Cmd+Shift+D shows its own source). Source: apps/forum/forum.c (about 2,400 lines), with forum.worklog.md.

villa

A property administered from a distance

A Roman villa is an estate you own and run from afar, with a staff working in your absence. villa looks after remote servers over plain ssh, and it is brownfield by design: the server it was built against already runs other services, so villa observes, nudges and remembers, and never takes the machine over. It checks services and units, nginx sites, disk, memory and uptime, runs actions with a hard timeout, and records what it saw as events.

The app file only wires; all the real work lives in villa_agens (the cycle, the remote check script, the events) and villa_lectores (pure parsers whose specification is real captured output), so the root test suite covers it. Nothing blocks: every check runs through processus's incremental path, one step per tick, because the house has no threads. And it is careful exactly where care is needed: locally no shell is ever used; remotely ssh always runs one, so unit names from the user's own records are validated before they enter the script, and ssh's failures are told apart by cause. Specs: project-specs/villa-spec-v2.md (the build blueprint) and its interview. Source: apps/villa/villa.c.

mensor

Reading the house's measurements

mensor is two programs on purpose. The command-line mensor is called on the hot path of every build, once per file, to record timings with mensura (nested, tied to a run, a machine and a commit). mensor -ui starts a separate binary, mensor_ui, a read-only explorer of those measurements in a vitrea window. They are separate because linking the window into the recorder would load AppKit and WebKit into every call during a build: in the header's words (translated), "the very flaw of the observer that the journal was meant to avoid, brought back through the back door".

It is small (about 450 lines). Moving it onto atrium gave it remote control (imperium) for free, and it became the first feature built under Fran's "drive the app you're building" loop, where manus let Claude add a session picker and verify it without a round trip. Its worklog records that building for drivability and for accessibility turned out to be the same work: real buttons with labels serve both the test hand and a screen reader. Source: apps/mensor/mensor_ui.c.

pictor

A painter: the first application built on ludus

pictor is a raster editor: a window, a sheet in a viewport, a brush, tools. It is the first consumer of the ludus stack and was built to prove it: the document is a stroke log in a volumen, state lives in islands checked by canons with an owner table (apps/pictor/canones/), the view is a pure componere function, drawing goes through figures into commands, and the whole loop runs in a dispensator that can be tested and replayed without a window. The app file itself is about 230 lines that connect these parts.

Its first build (2026-09-05) recorded the numbers: a closure of 41 house objects and 45 headers (about 2.2 MB of house source, plus SQLite through volumen), a warm build in 0.11 s, a 1.8 MB binary, and thirty frames with the worst at 2 ms. It also recorded a finding about the single-file build: the amalgamator would not carry a vendored unit, and SQLite is in pictor's closure through volumen, so a one-file pictor needs either an amalgamator that ships SQLite alongside or a document store without it. Development continues in its own worktree (../rhubarb-pictor). Source: apps/pictor/pictor.c and pictor.worklog.md; specs pictor-spec.md and the plans beside it.
