A1Turn off floating-point contraction in the house flags

decision from the Math library map review, 2026-10-05

What. Add -ffp-contract=off to the shared compiler flags in tools/vexilla.sh.

Why. The library map's float rules require it. Clang, our compiler, fuses a multiply and an add into one instruction within an expression by default on ARM64, which rounds once instead of twice. So the house's floating-point code can produce different bits from the same source built with other settings or on other machines. The flag is not set today (checked 2026-10-05).

Cost. One line, but it changes how every file is compiled, so every test suite has to be re-run before the commit. Float results could move in the last bit, which a golden test somewhere might notice.

A2Make 64-bit long long an explicit platform requirement

decision from the Math library map review, 2026-10-05

What. State that the house requires a 64-bit long long, and check it at build time with the C89 negative-array-size trick (a declaration that fails to compile if the size is wrong).

Why. The map lists "no guaranteed 64-bit integer" as a C89 hazard (long long is C99). The house has in effect already chosen: it compiles with -Wno-long-long, latina.h defines i64 and s64 as long long, and magnus relies on exact 64-bit intermediates. Writing the choice down and checking it turns an unstated assumption into a rule that fails loudly on a platform where it doesn't hold.

Cost. Small: a few lines in a widely included header (probably latina.h), which means most suites are owed again. The alternative, rebuilding the wide arithmetic on 16-bit pieces, would cost about four times the speed and is not recommended.

A3Performance tracking for the math libraries, then faster algorithms when measured

plan agreed 2026-10-05, after magnus and fractio landed

What, in order.

  1. Fix what the reviewer of magnus and fractio finds (a review agent was started 2026-10-05).
  2. Deterministic cost counters inside the math libraries (limb multiplications, allocations) behind a test-only switch. Counts are identical on every machine, so tests can assert them: "two 1000-limb numbers multiply in at most N limb products" catches an accidental quadratic path as a plain test failure, without timing noise.
  3. Wall-clock benchmarks recorded through mensura/mensor (machine id + commit, graphable), one probatio_<x>_benchmark.c per library on the pattern of probatio_flatura_benchmark.c: a fixed seeded workload at sizes 1, 2, 4 … 4096 limbs for multiply, divide, decimal conversion and gcd. Recorded, not gated. This is today's baseline.
  4. Faster algorithms only when a consumer needs big numbers, with thresholds read off the baseline curves, never copied from elsewhere: Karatsuba first (about 100 lines; crossover expected around 20–40 limbs); divide-and-conquer decimal conversion and Newton or Burnikel–Ziegler division, since Knuth D and the current conversion stay quadratic even after a faster multiply; NTT (exact, modulo primes with Chinese remaindering, never a floating-point FFT) for thousands of limbs, shared with fast polynomial multiplication (map #17). Toom–Cook only if a benchmark shows the middle band matters.

Why. The API does not change; only the inside does. Measuring first keeps us from optimizing multiplication while division, conversion and gcd (which fractio calls constantly) are the real costs.

A4piscina_vacare costs time proportional to capacity

note found by the second math-library review, 2026-10-05

What. piscina_vacare zeroes every byte of every block (memset over the full capacity) on each call. In a hot loop that is the dominant cost: magnus's gcd briefly called it once per Euclid step and became 2–5× slower on medium numbers. It now rolls back to a mark with piscina_reficere instead (no clearing).

Why it matters elsewhere. Any loop that empties an arena per iteration pays for the whole capacity each time. Options if it shows up again: a piscina_vacare without the clearing (callers that need zeroed memory zero what they allocate), or the mark-and-rollback pattern. Not changed house-wide; noted so the next hot loop knows.

A5The natura tests fail on a fresh checkout

bug found 2026-10-05 by tools/frigida_probare.sh before merging tertia into main

What. In a fresh worktree, probatio_natura_canones, _glossae and _quaesitor fail: they build bin/natura* through tools/natura_struere.sh, whose provenance step for the FIRST binary needs the aedilis manifests of all four (build/aedilis/natura_*/manifestum.stml), which a fresh tree does not have. Main at 13064eed fails identically, so it predates the tertia merge; the other 13 suites are green fresh.

Workaround (used in tertia): run bin/aedilis tools/<x>.c for the four natura tools first, then ./tools/natura_struere.sh. Fix: have the build script (or the fabrica action) produce the manifests before the provenance step, so "green on a fresh clone" holds again.

A6Future library: roaring bitmaps (compressed integer sets)

idea agreed as a someday library, 2026-10-06, while discussing polynomium's dense memory

What. Sets of 32-bit integers, compressed by splitting the space into chunks of 216 and choosing the representation per chunk: a sorted array of 16-bit values when sparse, a raw 8 KB bitmap when dense, runs when clustered. Fast union, intersection, difference, membership, rank and iteration; a stable serialized form.

Why. The standard structure for inverted indexes and posting lists ("which documents contain this word", set intersections in queries). Consumers would be the future database and search work, and possibly the house's own indexes (silva's symbol index, census and ledger queries). Clearly bounded, independent of everything else, and a good benchmark subject. Not related to the math stack except in idea: the same dense-or-sparse-per-region choice could later give a sparse polynomial type for multivariate work (HOMFLY), where dense storage is hopeless.

A8Modular Hermite and Smith when matrix sizes grow

idea 2026-10-06, measured when matrix v2 landed

Update 2026-10-06. The review found the Bézout version blowing up (Hermite 36×36: 22.6 s); switching to smallest-pivot Euclid made it 11 ms and Smith with U, V at 40×40 46 ms. Modular methods are now only for genuinely large matrices.

What. matrix_forma_hermite and matrix_forma_smith use classical elimination (now Euclid, smallest pivot first), whose intermediate entries still grow with size: Hermite 60×60 takes 112 ms with a ~0.9 MB scratch peak. Modular methods (Domich–Kannan–Trotter Hermite modulo the determinant; Smith via the determinant modulus) keep entries bounded and can replace the internals without changing the API or the certificates.

Why later. No consumer needs big matrices yet (knot Seifert matrices and small homology computations are tiny); the agenda A3 benchmarks should decide when.

D1Arena allocations aligned by default

done dfa6a05a, 2026-10-05; decided by Fran the same day

piscina_allocare now aligns to 8 bytes, like malloc (PISCINA_ORDINATIO_ORDINARIA); tight byte packing stays available as piscina_allocare_ordinatum(p, n, I). Found by the first math-library review agent: magnus limbs, and credo's own records, sat at misaligned addresses (undefined behaviour; 95 sanitizer reports, now 0). All 14 suites were run: exact byte-usage expectations moved by their padding (about 0.02% more memory at most), and the change exposed a latent use-after-rollback bug in probatio_volumen, fixed.
